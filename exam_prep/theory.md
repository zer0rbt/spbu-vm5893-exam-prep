## Тема 1. Основы машинного обучения

### Билет 1.1

> Постановка задачи классификации. Примеры задач классификации. Типы алгоритмов классификации.

**Ответ.**

**Постановка.** Дано множество объектов $X$ и конечное множество меток $Y = \{1,\dots,K\}$.
Существует неизвестная целевая зависимость $y^*: X \to Y$, известная только на обучающей выборке
$D = \{(x_i, y_i)\}_{i=1}^{\ell}$, где $x_i \in \mathbb{R}^d$ — вектор признаков. Требуется построить
алгоритм $a: X \to Y$, приближающий $y^*$ на всём $X$, т.е. минимизирующий ожидаемый риск
$R(a) = \mathbb{E}_{(x,y)\sim P}[L(a(x), y)]$. На практике минимизируется эмпирический риск
$\hat{R}(a) = \frac{1}{\ell}\sum_i L(a(x_i), y_i)$.

Виды: бинарная ($K=2$), многоклассовая ($K>2$), многометочная (объекту сопоставляется подмножество меток).

**Метрики качества:** accuracy, precision $= TP/(TP+FP)$, recall $= TP/(TP+FN)$,
$F_1 = 2PR/(P+R)$, ROC-AUC. При несбалансированных классах accuracy неинформативна.

**Примеры задач:** спам-фильтрация писем, кредитный скоринг (выдать/не выдать), медицинская
диагностика по анализам, распознавание рукописных цифр, определение тональности отзыва,
детекция мошеннических транзакций.

**Типы алгоритмов:**
- *метрические* (ленивые, lazy) — k-NN, метод парзеновского окна: основаны на гипотезе
  компактности и функции расстояния;
- *логические* — решающие деревья, решающие списки, композиции (Random Forest, градиентный бустинг);
- *линейные / разделяющие поверхности* — логистическая регрессия, SVM, персептрон;
- *вероятностные (байесовские)* — наивный байесовский классификатор, LDA/QDA;
- *нейросетевые* — многослойный перцептрон, CNN, трансформеры;
- *композиции (ансамбли)* — бэггинг, бустинг, стекинг.

Отдельно различают **порождающие** (моделируют $p(x\mid y)$ и применяют формулу Байеса) и
**дискриминативные** (моделируют $p(y \mid x)$ или сразу границу) модели.

### Билет 1.2

> Метрические алгоритмы классификации. k-NN.

**Ответ.**

**Идея (гипотеза компактности):** близкие в пространстве признаков объекты чаще принадлежат
одному классу. Задаётся метрика $\rho(x, x')$ — обычно евклидова
$\rho(x,x')=\sqrt{\sum_j (x_j-x'_j)^2}$, также манхэттенская, Минковского, косинусная,
Хэмминга (для категориальных).

**Алгоритм k ближайших соседей.** Для объекта $u$ обучающая выборка сортируется по
возрастанию расстояния до $u$: $x_{(1)}^u, \dots, x_{(\ell)}^u$. Ответ — мажоритарное
голосование $k$ ближайших:
$$a(u) = \arg\max_{y \in Y} \sum_{i=1}^{k} [\,y_{(i)}^u = y\,]$$
Обобщение — взвешенное голосование с весами $w_i$, убывающими по $i$ или по расстоянию
(например $w_i = 1/\rho(u, x_{(i)})$, метод парзеновского окна с ядром $K(\rho/h)$).

**Свойства и практика.**
- Обучения как такового нет («ленивый» алгоритм»), вся работа — на этапе предсказания:
  наивная сложность $O(\ell d)$ на объект; ускоряется KD-tree / ball-tree / HNSW.
- $k$ подбирается по кросс-валидации: $k=1$ → переобучение и чувствительность к шуму,
  слишком большое $k$ → недообучение (в пределе — константный ответ мажоритарного класса).
- Обязательна нормировка признаков (иначе признак с большим масштабом доминирует в метрике).
- Страдает от «проклятия размерности»: при больших $d$ расстояния между всеми точками
  становятся близкими.
- Плюсы: простота, интерпретируемость (можно предъявить соседей-прецеденты), работает
  с произвольным числом классов; применяется в рекомендательных системах и поиске похожих.

### Билет 1.3

> Логистические методы классификации. Деревья решений.

**Ответ.**

**Логистическая регрессия.** Линейная модель для $y \in \{0,1\}$; вероятность класса задаётся
сигмоидой от линейной комбинации признаков:
$$p(y=1 \mid x) = \sigma(w^\top x + w_0), \qquad \sigma(z) = \frac{1}{1+e^{-z}}$$
Параметры $w$ ищутся методом максимального правдоподобия, что эквивалентно минимизации
логистических потерь (log-loss / бинарной кросс-энтропии):
$$L(w) = -\sum_{i=1}^{\ell}\big[y_i \ln p_i + (1-y_i)\ln(1-p_i)\big] \to \min_w$$
Функция выпуклая, минимизируется градиентным спуском / IRLS; в аналитическом виде решения нет.
Добавляют $L_1$/$L_2$-регуляризацию. Разделяющая поверхность — гиперплоскость $w^\top x + w_0 = 0$;
классификация — сравнение $p$ с порогом (обычно 0.5, порог настраивается по ROC/PR-кривой).
Плюсы: калиброванные вероятности, интерпретируемые веса (логит-шансы:
$\ln\frac{p}{1-p}=w^\top x + w_0$), быстрое обучение на больших разреженных данных.
Многоклассовое обобщение — softmax-регрессия. Пример: кредитный скоринг, CTR-предсказание.

**Решающие деревья.** Бинарное дерево, во внутренних вершинах — предикаты вида
$[x_j \le t]$, в листьях — ответ (мажоритарный класс или вектор вероятностей). Строятся
жадно, сверху вниз (CART, ID3, C4.5): в каждой вершине выбирается признак и порог,
максимизирующие прирост информации
$$\text{Gain} = H(S) - \frac{|S_L|}{|S|}H(S_L) - \frac{|S_R|}{|S|}H(S_R)$$
где критерий неоднородности $H$ — энтропия $-\sum_k p_k \log_2 p_k$ или индекс Джини
$1-\sum_k p_k^2$ (для регрессии — дисперсия/MSE).
Критерии остановки: максимальная глубина, минимальное число объектов в листе, нулевой прирост.
Против переобучения — предобрезка (ограничения) и постобрезка (pruning).
Плюсы: интерпретируемость, не требуется нормировка, работа со смешанными типами признаков,
устойчивость к выбросам, автоматический отбор признаков.
Минусы: неустойчивость (малое изменение выборки → другое дерево), склонность к переобучению,
кусочно-постоянные ступенчатые границы. Поэтому на практике используются ансамбли:
Random Forest (бэггинг + случайные подпространства) и градиентный бустинг (XGBoost, CatBoost, LightGBM).

### Билет 1.4

> Постановка задачи кластеризации. Примеры задач кластеризации. Типы алгоритмов кластеризации.

**Ответ.**

**Постановка.** Дана выборка $X = \{x_1,\dots,x_\ell\}$ **без меток** (обучение без учителя).
Требуется разбить её на группы (кластеры) так, чтобы объекты внутри кластера были похожи
(расстояние мало), а объекты из разных кластеров — различны. Формально: найти
$a: X \to \{1,\dots,K\}$, оптимизирующее функционал качества, например
$$\sum_{k=1}^{K}\sum_{x_i \in C_k} \rho^2(x_i, \mu_k) \to \min$$
Задача **некорректно поставлена**: «правильного» ответа нет, результат зависит от метрики,
числа кластеров и критерия; число кластеров $K$ часто неизвестно.

**Метрики качества:** внутренние — силуэт (silhouette), индекс Данна, Калински–Харабаса;
внешние (при наличии эталонной разметки) — ARI, NMI, полнота/однородность.

**Примеры задач:** сегментация клиентов для маркетинга, группировка новостей по сюжетам,
сжатие изображений (квантование цветов), сегментация изображений, поиск сообществ в соцсетях,
обнаружение аномалий, предварительное разведочное разбиение данных перед обучением с учителем.

**Типы алгоритмов:**
- *иерархические* (агломеративные и дивизимные) — строят дендрограмму;
- *основанные на прототипах / центроидах* — k-средних, k-medoids (PAM), c-means (нечёткая);
- *плотностные* — DBSCAN, OPTICS, mean-shift: находят кластеры произвольной формы и выделяют шум;
- *вероятностные (модельные)* — смеси гауссиан (GMM), обучаемые EM-алгоритмом; дают мягкое
  (нечёткое) разбиение;
- *графовые/спектральные* — спектральная кластеризация, выделение компонент связности;
- *сеточные и для больших данных* — CLIQUE, BIRCH, MiniBatchKMeans.

Разбиения бывают **чёткие** (объект в одном кластере) и **нечёткие** (степени принадлежности),
**плоские** и **иерархические**.

### Билет 1.5

> Алгоритм Иерархической кластеризации. Алгоритм k-средних.

**Ответ.**

**Иерархическая (агломеративная) кластеризация.**
1. Каждый объект — отдельный кластер ($\ell$ кластеров).
2. Находим пару ближайших кластеров и объединяем их.
3. Пересчитываем расстояния (формула Ланса–Уильямса) и повторяем, пока не останется один кластер.

Результат — **дендрограмма**; горизонтальный разрез на нужной высоте даёт разбиение на $K$ кластеров.
Способы измерения расстояния между кластерами (linkage):
- single link: $\min_{a\in A, b\in B}\rho(a,b)$ — вытянутые «цепочечные» кластеры;
- complete link: $\max \rho(a,b)$ — компактные шарообразные;
- average link (UPGMA): среднее попарное;
- Ward: минимизация прироста внутрикластерной дисперсии (на практике чаще всего).

Свойства: $K$ заранее не нужен, детерминирован, даёт наглядную структуру вложенности;
но сложность $O(\ell^3)$ (в лучших реализациях $O(\ell^2 \log \ell)$) и память $O(\ell^2)$ —
не масштабируется на большие данные; объединение необратимо (жадность). Дивизимный вариант
работает сверху вниз: один кластер последовательно делится.

**Алгоритм k-средних (Ллойда).** Минимизирует суммарную внутрикластерную сумму квадратов
(inertia): $J = \sum_{k}\sum_{x \in C_k}\|x-\mu_k\|^2$.
1. Выбрать $K$ и инициализировать центроиды (случайно или k-means++).
2. **E-шаг:** отнести каждый объект к ближайшему центроиду: $c_i = \arg\min_k \|x_i - \mu_k\|$.
3. **M-шаг:** пересчитать центроиды как средние своих кластеров: $\mu_k = \frac{1}{|C_k|}\sum_{x\in C_k} x$.
4. Повторять 2–3 до стабилизации разбиения.

Свойства: сложность $O(\ell K d I)$ — линейна по числу объектов, поэтому применим к большим
данным; $J$ монотонно убывает, сходимость за конечное число шагов, но **только к локальному
минимуму** → несколько запусков с разной инициализацией (n_init) или k-means++.
Ограничения: нужно задавать $K$ (подбирают «методом локтя» по $J(K)$ или по силуэту),
находит только выпуклые примерно шарообразные кластеры одинакового масштаба, чувствителен
к выбросам (среднее не робастно — отсюда k-medoids) и к масштабу признаков (нужна нормировка).

## Тема 2. Теория вероятностей и математическая статистика

### Билет 2.1

> Основные понятия теории вероятностей и математической статистики (отношения между событиями. Невозможное, достоверное, противоположное события. Независимость случайных событий. Попарная независимость и независимость в совокупности).

**Ответ.**

**Вероятностное пространство** — тройка $(\Omega, \mathcal{F}, P)$: $\Omega$ — пространство
элементарных исходов, $\mathcal{F}$ — $\sigma$-алгебра событий (замкнута относительно
дополнения и счётных объединений), $P:\mathcal{F}\to[0,1]$ — вероятностная мера, удовлетворяющая
аксиомам Колмогорова: $P(A)\ge 0$, $P(\Omega)=1$, счётная аддитивность
$P(\bigsqcup_i A_i)=\sum_i P(A_i)$ для попарно несовместных $A_i$.

**События и отношения между ними:**
- $\Omega$ — **достоверное** событие, $P(\Omega)=1$; $\varnothing$ — **невозможное**, $P(\varnothing)=0$;
- **противоположное** $\bar{A}=\Omega\setminus A$, $P(\bar{A}) = 1-P(A)$;
- $A \subset B$ — $A$ влечёт $B$; сумма $A\cup B$ (хотя бы одно), произведение $A\cap B$ (оба),
  разность $A\setminus B$;
- **несовместные** (непересекающиеся) события: $A\cap B=\varnothing$;
- **полная группа**: попарно несовместны и в объединении дают $\Omega$.

Формула сложения: $P(A\cup B)=P(A)+P(B)-P(A\cap B)$.
Условная вероятность: $P(A\mid B) = \dfrac{P(A\cap B)}{P(B)}$, $P(B)>0$.
Формула полной вероятности: $P(A)=\sum_i P(A\mid H_i)P(H_i)$ для полной группы гипотез $H_i$.
Формула Байеса: $P(H_i \mid A) = \dfrac{P(A\mid H_i)P(H_i)}{P(A)}$ — основа наивного
байесовского классификатора.

**Независимость событий.** $A$ и $B$ независимы, если
$$P(A\cap B)=P(A)P(B) \iff P(A\mid B)=P(A)$$
- **Попарная независимость** событий $A_1,\dots,A_n$: $P(A_iA_j)=P(A_i)P(A_j)$ для всех $i\ne j$.
- **Независимость в совокупности**: для *любого* поднабора индексов
  $P(A_{i_1}\cdots A_{i_k})=\prod_{j} P(A_{i_j})$, т.е. должны выполняться все $2^n-n-1$ равенств.

Независимость в совокупности влечёт попарную, **обратное неверно**. Классический контрпример
Бернштейна: тетраэдр с гранями, окрашенными в красный, синий, зелёный и все три цвета;
события «выпала грань с красным/синим/зелёным» имеют $P=1/2$ и попарно независимы
($P(A_iA_j)=1/4$), но $P(A_1A_2A_3)=1/4 \ne 1/8$.

**Математическая статистика** решает обратную задачу: по выборке $X_1,\dots,X_n$ (независимые
одинаково распределённые случайные величины) оценить неизвестное распределение или его
параметры — точечные оценки (метод моментов, метод максимального правдоподобия), их свойства
(несмещённость, состоятельность, эффективность), доверительные интервалы, проверка гипотез.

### Билет 2.2

> Понятие случайной величины. Классификация случайных величин.

**Ответ.**

**Определение.** Случайная величина $\xi$ — измеримая функция $\xi:\Omega\to\mathbb{R}$, т.е.
такая, что для любого $x\in\mathbb{R}$ множество $\{\omega: \xi(\omega) < x\}$ принадлежит
$\sigma$-алгебре $\mathcal{F}$ (является событием). Измеримость нужна, чтобы для любого
разумного множества $B$ была определена вероятность $P(\xi \in B)$.

**Классификация по типу распределения:**
1. **Дискретные** — принимают не более чем счётное множество значений $x_1,x_2,\dots$;
   задаются рядом распределения $p_i=P(\xi=x_i)$, $\sum_i p_i = 1$.
   Примеры: бернуллиевская $B(p)$, биномиальная $Bi(n,p)$, геометрическая, пуассоновская
   $P(\lambda)$, дискретная равномерная.
2. **Непрерывные (абсолютно непрерывные)** — функция распределения представима как
   $F(x)=\int_{-\infty}^{x} f(t)\,dt$, где $f\ge 0$ — плотность, $\int_{\mathbb R} f = 1$;
   $P(\xi = x) = 0$ для любой точки. Примеры: равномерное $U[a,b]$, нормальное $N(\mu,\sigma^2)$,
   экспоненциальное $\mathrm{Exp}(\lambda)$, $\chi^2$, Стьюдента, Фишера.
3. **Сингулярные** — $F$ непрерывна, но растёт на множестве нулевой меры Лебега (лестница
   Кантора); плотности не существует.
4. **Смешанные** — комбинация дискретной и непрерывной компонент (пример: время ожидания,
   равное нулю с положительной вероятностью).

По размерности различают скалярные величины и случайные векторы; по типу шкалы —
количественные и категориальные (номинальные/порядковые) признаки в задачах анализа данных.

### Билет 2.3

> Функция распределения случайной величины, ее свойства.

**Ответ.**

**Определение.** $F_\xi(x) = P(\xi < x)$ (в ряде учебников $P(\xi \le x)$; различие — в
непрерывности слева/справа). Функция распределения задаёт распределение случайной величины
однозначно и существует для любого типа величины — этим она удобнее плотности и ряда распределения.

**Свойства:**
1. $0 \le F(x) \le 1$;
2. неубывающая: $x_1 < x_2 \Rightarrow F(x_1)\le F(x_2)$;
3. $\lim_{x\to-\infty}F(x)=0$, $\lim_{x\to+\infty}F(x)=1$;
4. непрерывна слева (для определения через $P(\xi<x)$), в каждой точке существуют односторонние
   пределы; точек разрыва не более чем счётное число, величина скачка равна $P(\xi=x)$;
5. $P(a \le \xi < b) = F(b)-F(a)$;
6. для абсолютно непрерывной величины $F'(x)=f(x)$ в точках непрерывности плотности.

Любая функция со свойствами 1–4 является функцией распределения некоторой случайной величины.

**Применение в анализе данных:** эмпирическая функция распределения
$\hat{F}_n(x)=\frac{1}{n}\sum_i [X_i < x]$ — состоятельная оценка $F$ (теорема Гливенко–Кантелли);
на ней основаны критерии согласия Колмогорова–Смирнова, квантили, QQ-графики,
метод обратной функции для генерации случайных чисел ($\xi = F^{-1}(U)$, $U\sim U[0,1]$).

### Билет 2.4

> Числовые характеристики случайных величин. Начальный и центральный моменты. Математическое ожидание, его свойства. Дисперсия случайной величины, ее свойства.

**Ответ.**

**Начальный момент** порядка $k$: $\alpha_k = \mathbb{E}\xi^k$.
**Центральный момент** порядка $k$: $\mu_k = \mathbb{E}(\xi - \mathbb{E}\xi)^k$.
$\mu_1 = 0$, $\mu_2 = D\xi$; $\mu_3$ определяет асимметрию $\gamma_1=\mu_3/\sigma^3$,
$\mu_4$ — эксцесс $\gamma_2 = \mu_4/\sigma^4 - 3$.

**Математическое ожидание** (среднее значение):
$$\mathbb{E}\xi = \sum_i x_i p_i \quad\text{(дискр.)}, \qquad \mathbb{E}\xi = \int_{-\infty}^{+\infty} x f(x)\,dx \quad\text{(непр.)}$$
существует, если ряд/интеграл сходится абсолютно (у распределения Коши матожидания нет).

*Свойства:* $\mathbb{E}c = c$; линейность $\mathbb{E}(a\xi+b\eta)=a\mathbb{E}\xi+b\mathbb{E}\eta$
(без предположения независимости); монотонность ($\xi\le\eta \Rightarrow \mathbb{E}\xi\le\mathbb{E}\eta$);
для **независимых** $\mathbb{E}(\xi\eta)=\mathbb{E}\xi\,\mathbb{E}\eta$;
$\mathbb{E}g(\xi)=\int g(x)f(x)dx$.

**Дисперсия** — мера рассеяния вокруг среднего:
$$D\xi = \mathbb{E}(\xi-\mathbb{E}\xi)^2 = \mathbb{E}\xi^2 - (\mathbb{E}\xi)^2 \ge 0$$
Среднеквадратическое отклонение $\sigma = \sqrt{D\xi}$ измеряется в тех же единицах, что и $\xi$.

*Свойства:* $Dc=0$; $D(c\xi)=c^2 D\xi$; $D(\xi+c)=D\xi$;
$D(\xi\pm\eta)=D\xi+D\eta\pm 2\,\mathrm{cov}(\xi,\eta)$, и для независимых (достаточно
некоррелированных) $D(\xi+\eta)=D\xi+D\eta$; $D\xi = 0 \iff \xi = \text{const}$ почти наверное.

Другие характеристики: медиана и квантили (робастны к выбросам, в отличие от среднего), мода,
ковариация $\mathrm{cov}(\xi,\eta)=\mathbb{E}(\xi-\mathbb{E}\xi)(\eta-\mathbb{E}\eta)$.

*Статистические аналоги:* выборочное среднее $\bar{X}=\frac1n\sum X_i$ (несмещённая состоятельная
оценка $\mathbb{E}\xi$) и **несмещённая** выборочная дисперсия $s^2=\frac{1}{n-1}\sum (X_i-\bar X)^2$
(делитель $n-1$ — поправка Бесселя; с делителем $n$ оценка смещена вниз).
Практическое значение: неравенство Чебышёва $P(|\xi-\mathbb{E}\xi|\ge \varepsilon)\le D\xi/\varepsilon^2$,
закон больших чисел, ЦПТ; в анализе данных — стандартизация признаков $z=(x-\bar x)/s$,
волатильность как $\sigma$ доходностей.

### Билет 2.5

> Элементы корреляционного анализа. Парная линейная регрессия.

**Ответ.**

**Ковариация:** $\mathrm{cov}(X,Y)=\mathbb{E}(X-\mathbb{E}X)(Y-\mathbb{E}Y)=\mathbb{E}XY-\mathbb{E}X\,\mathbb{E}Y$.
Зависит от единиц измерения, поэтому нормируют.

**Коэффициент корреляции Пирсона:**
$$r_{XY}=\frac{\mathrm{cov}(X,Y)}{\sigma_X \sigma_Y}, \qquad
\hat{r}=\frac{\sum_i (x_i-\bar x)(y_i-\bar y)}{\sqrt{\sum_i (x_i-\bar x)^2 \sum_i (y_i-\bar y)^2}}$$

*Свойства:* $-1\le r \le 1$; $|r|=1$ тогда и только тогда, когда между $X$ и $Y$ есть точная
линейная зависимость $Y=aX+b$ (знак $r$ = знак $a$); $r$ не меняется при линейных преобразованиях
с положительными коэффициентами; независимость $\Rightarrow r=0$, **обратное неверно**
($r$ измеряет только линейную связь: для $Y=X^2$, $X\sim U[-1,1]$ имеем $r=0$ при полной
зависимости). Значимость проверяется критерием $t = r\sqrt{n-2}/\sqrt{1-r^2}$ с $n-2$ степенями свободы.
Для монотонных нелинейных связей и порядковых данных используют ранговые коэффициенты
Спирмена и Кендалла. Важно: **корреляция не означает причинно-следственную связь**
(возможен общий скрытый фактор или ложная корреляция).

**Парная линейная регрессия.** Модель: $y_i = \beta_0 + \beta_1 x_i + \varepsilon_i$, где
$\varepsilon_i$ — случайные ошибки с $\mathbb{E}\varepsilon=0$, $D\varepsilon=\sigma^2$
(условия Гаусса–Маркова: некоррелированность, гомоскедастичность).
Оценки **метода наименьших квадратов** минимизируют $\sum_i (y_i-\beta_0-\beta_1 x_i)^2$:
$$\hat{\beta_1} = \frac{\sum (x_i-\bar x)(y_i-\bar y)}{\sum (x_i-\bar x)^2} = r_{xy}\frac{s_y}{s_x},
\qquad \hat{\beta_0}=\bar y - \hat{\beta_1}\bar x$$
Прямая всегда проходит через точку $(\bar x, \bar y)$. По теореме Гаусса–Маркова МНК-оценки —
наилучшие линейные несмещённые (BLUE).

**Качество модели:** коэффициент детерминации
$$R^2 = 1-\frac{\sum(y_i-\hat y_i)^2}{\sum (y_i-\bar y)^2} \in [0,1],$$
доля объяснённой дисперсии; в парной регрессии $R^2=r_{xy}^2$. Диагностика — анализ остатков
(случайность, нормальность, отсутствие гетероскедастичности), проверка значимости $\beta_1$
по $t$-критерию. Пример применения: зависимость цены квартиры от площади, прогноз объёма
продаж от расходов на рекламу, оценка беты актива относительно индекса.

## Тема 3. Основы программирования на Python

### Билет 3.1

> Основные синтаксические конструкции, REPL.

**Ответ.**

Python — высокоуровневый интерпретируемый язык с динамической строгой типизацией,
автоматическим управлением памятью, поддержкой процедурной, ООП и функциональной парадигм.
Блоки выделяются **отступами** (обычно 4 пробела), а не скобками; конец строки — конец инструкции.

**Типы данных:** неизменяемые — `int` (длинная арифметика), `float`, `bool`, `str`, `tuple`,
`frozenset`, `bytes`; изменяемые — `list`, `dict` (с версии 3.7 сохраняет порядок вставки),
`set`, `bytearray`. Переменная — имя, связанное с объектом (ссылочная семантика).

**Конструкции:**
- ветвление `if / elif / else`, тернарное выражение `a if cond else b`, с 3.10 — `match/case`;
- циклы `for x in iterable:` и `while cond:` с `break`, `continue` и необязательным `else`;
- функции `def f(a, b=0, *args, **kwargs): return ...`, лямбды, замыкания, декораторы,
  генераторы (`yield`);
- классы `class A(Base): def __init__(self): ...`, магические методы, наследование (в т.ч. множественное);
- обработка исключений `try / except / else / finally`, `raise`, менеджеры контекста `with`;
- модули и пакеты: `import`, `from ... import ...`, `if __name__ == "__main__":`;
- «питонические» идиомы: списковые/словарные включения `[f(x) for x in xs if p(x)]`,
  распаковка `a, *rest = xs`, `enumerate`, `zip`, срезы `xs[a:b:c]`, f-строки `f"{x:.2f}"`.

**REPL** (Read–Eval–Print Loop) — интерактивный цикл «прочитать → вычислить → напечатать →
повторить». Запускается командой `python` без аргументов; приглашение `>>>` (продолжение `...`),
результат выражения печатается автоматически, последнее значение доступно как `_`.
Полезен для быстрых экспериментов, знакомства с API (`dir()`, `help()`), отладки.
Улучшенные оболочки: IPython (магические команды `%timeit`, `%run`, автодополнение),
`python -i script.py` — вход в REPL после выполнения скрипта, `breakpoint()` → pdb.
Стиль кода регламентирован PEP 8, документирование — docstring (PEP 257).

### Билет 3.2

> Jupyter. Организация работы. Типовая организация проекта, виртуальные окружения, управление зависимостями pip, pip-env, poetry.

**Ответ.**

**Jupyter Notebook / JupyterLab** — среда интерактивных вычислений: документ `.ipynb` (JSON)
состоит из ячеек кода, Markdown и сохранённого вывода (графики, таблицы). Архитектура:
браузерный клиент ↔ сервер ↔ **ядро** (kernel, отдельный процесс интерпретатора), обмен через
ZeroMQ. Состояние (переменные) живёт в ядре между ячейками, поэтому важен порядок выполнения;
`Restart & Run All` — проверка воспроизводимости. Магические команды: `%timeit`, `%matplotlib inline`,
`%%bash`, `!pip install`. Плюсы — быстрый исследовательский анализ (EDA), наглядность,
литературное программирование; минусы — скрытое состояние, плохая работа с git (диффы JSON,
решается `nbstripout`/`jupytext`), сложность тестирования → зрелый код выносят в модули `.py`
и импортируют в ноутбук.

**Типовая организация проекта:**
```
project/
├── src/mypkg/        # исходный код пакета (__init__.py, модули)
├── tests/            # тесты (pytest)
├── notebooks/        # исследовательские ноутбуки
├── data/             # raw / interim / processed (в git не коммитится)
├── pyproject.toml    # метаданные, зависимости, настройки инструментов (PEP 518/621)
├── requirements.txt  # либо lock-файл
├── .gitignore, README.md
```

**Виртуальное окружение** — изолированный каталог с собственным интерпретатором и `site-packages`.
Решает проблему конфликта версий между проектами и «загрязнения» системного Python.
Создание: `python -m venv .venv`, активация `source .venv/bin/activate`
(Windows: `.venv\Scripts\activate`), деактивация `deactivate`.

**Менеджеры зависимостей:**
- **pip** — стандартный установщик из PyPI: `pip install pandas==2.2.0`,
  `pip freeze > requirements.txt`, `pip install -r requirements.txt`. Прост, но не разрешает
  конфликты зависимостей полноценно и не разделяет «прямые» и «транзитивные» зависимости.
- **pipenv** — связка pip + venv: `Pipfile` (объявленные зависимости, отдельно dev-группа) и
  `Pipfile.lock` (точные версии + хеши → воспроизводимость сборки). Команды `pipenv install`,
  `pipenv shell`.
- **poetry** — полноценный менеджер проекта и сборки: `pyproject.toml` + `poetry.lock`,
  разрешение зависимостей SAT-солвером, группы зависимостей, `poetry add`, `poetry install`,
  сборка и публикация пакета `poetry build/publish`. Современные альтернативы — `uv`, `conda`
  (последняя удобна для научного стека и не-Python зависимостей).

Для полной воспроизводимости окружение дополнительно фиксируют в Docker-образе.

### Билет 3.3

> Аннотации типов, статистический анализ.

**Ответ.**

**Аннотации типов** (PEP 484, синтаксис переменных — PEP 526) — необязательные подсказки о типах:
```python
def mean(xs: list[float], *, default: float | None = None) -> float | None: ...
count: int = 0
```
Интерпретатор их **не проверяет** во время выполнения (динамическая типизация сохраняется),
он лишь сохраняет их в `__annotations__`; проверка — задача внешних инструментов.
Средства модуля `typing`: `Optional`, `Union` (или `|` с 3.10), `Any`, `Callable`, `Iterable`,
`TypeVar` и Generic для обобщённого кода, `Protocol` (структурная типизация, «утиная типизация»
статически), `Literal`, `TypedDict`, `NewType`, `cast`, `@overload`. Для отложенного вычисления
аннотаций — `from __future__ import annotations`.

*Зачем:* документация, самопроверяемая компилятором; автодополнение и рефакторинг в IDE;
раннее обнаружение ошибок; критично для больших кодовых баз и командной работы.
*Минусы:* многословность, необходимость поддерживать аннотации в актуальном состоянии.

**Статический анализ** — проверка кода без его выполнения:
- **проверка типов**: `mypy`, `pyright`/Pylance, `pyre`; постепенная типизация (gradual typing),
  режим `--strict`;
- **линтеры** — поиск ошибок и нарушений стиля: `ruff` (быстрый, на Rust, заменяет большинство),
  `flake8`, `pylint`, PEP 8;
- **форматтеры**: `black`, `isort`, `ruff format` — единый стиль без споров в ревью;
- **безопасность**: `bandit`, аудит зависимостей `pip-audit`;
- внедрение в процесс: pre-commit хуки и CI (GitHub Actions) — код не проходит в main,
  пока не пройдены линтеры, типы и тесты.

Динамические (runtime) проверки — отдельная задача: `pydantic`, `dataclasses` + валидация,
`typeguard`.

### Билет 3.4

> Проблемы интерпретатора, управление памятью, GIL.

**Ответ.**

**Модель выполнения CPython.** Исходный код компилируется в байт-код (`.pyc`), исполняемый
виртуальной машиной. Отсюда основные проблемы: низкая скорость по сравнению с компилируемыми
языками (в десятки раз), большой объём памяти на объект (всё — объект с заголовком: счётчик
ссылок + указатель на тип; `int` в Python занимает ~28 байт против 8 в C), динамическая
диспетчеризация атрибутов через словари.

**Управление памятью.** Все объекты размещаются в приватной куче интерпретатора,
у CPython есть собственный аллокатор (pymalloc: arenas → pools → blocks), уменьшающий число
системных вызовов и фрагментацию.
1. **Подсчёт ссылок** (reference counting) — основной механизм: у каждого объекта поле
   `ob_refcnt`; при достижении нуля объект немедленно освобождается. Плюс — детерминированность;
   минус — накладные расходы и **неспособность освободить циклические ссылки**.
2. **Сборщик мусора поколений** (модуль `gc`) — дополняет подсчёт ссылок, находит недостижимые
   циклы. Три поколения: новые объекты в поколении 0, пережившие сборку переходят дальше
   (гипотеза о поколениях: большинство объектов умирает молодыми). Можно управлять:
   `gc.disable()`, `gc.collect()`.
Оптимизации: кеширование малых `int` (−5…256) и интернирование строк, `__slots__` для
экономии памяти в классах, слабые ссылки `weakref`.

**GIL (Global Interpreter Lock)** — глобальная блокировка интерпретатора: в один момент времени
байт-код может исполнять только **один** поток процесса. Нужна для защиты счётчиков ссылок и
внутренних структур от гонок, упрощает C-API и ускоряет однопоточный код.
*Следствие:* многопоточность (`threading`) **не даёт ускорения на CPU-bound задачах** (потоки
конкурируют за GIL и переключаются каждые ~5 мс), но полезна для **I/O-bound** задач — при
операциях ввода-вывода, ожидании сети, а также внутри C-расширений (NumPy, pandas, zlib) GIL
освобождается.
*Обходные пути:* `multiprocessing` (несколько процессов, у каждого свой GIL), `asyncio`
(кооперативная многозадачность в одном потоке для I/O), вынос вычислений в C/Cython/Numba/
векторизованный NumPy, альтернативные реализации (Jython, IronPython без GIL, PyPy с JIT),
в Python 3.13 — экспериментальный free-threaded режим (PEP 703) и субинтерпретаторы (PEP 554).

### Билет 3.5

> Многопроцессорная обработка данных (Multiprocessing).

**Ответ.**

Модуль `multiprocessing` порождает **отдельные процессы** ОС, каждый со своим интерпретатором
и своим GIL, что даёт реальный параллелизм на многоядерных CPU для вычислительных задач.

**Основные средства:**
- `Process(target=f, args=(...))` + `start()`, `join()` — низкоуровневый запуск;
- `Pool` — пул воркеров и высокоуровневые операции: `map`, `imap`, `starmap`, `apply_async`;
  типичный паттерн data-parallel обработки (разбить данные на чанки → обработать → собрать);
- `concurrent.futures.ProcessPoolExecutor` — унифицированный современный API (тот же интерфейс,
  что и у `ThreadPoolExecutor`, легко переключаться);
- обмен данными: `Queue`, `Pipe` (сериализация через `pickle`), разделяемая память
  `Value`, `Array`, `shared_memory` (без копирования — важно для больших массивов);
- синхронизация: `Lock`, `Semaphore`, `Event`, `Barrier`, `Manager` для разделяемых объектов.

**Способы порождения процессов:** `fork` (быстро, Unix, копирование при записи; небезопасен
с потоками), `spawn` (Windows и macOS по умолчанию — новый интерпретатор, дороже, требует
защиты точки входа `if __name__ == "__main__":`, иначе бесконечное порождение процессов),
`forkserver`.

**Накладные расходы и ограничения:** создание процесса дорого; все аргументы и результаты
сериализуются через pickle (лямбды и локальные функции непикуемы); память не разделяется —
дублирование данных; отладка сложнее. Поэтому выигрыш есть только при достаточно крупных
независимых порциях работы (CPU-bound). Для I/O-bound задач дешевле потоки/asyncio.

**Правило выбора:** CPU-bound → процессы (или векторизация/C-расширения); I/O-bound → потоки
или `asyncio`. Для по-настоящему больших данных — распределённые фреймворки: Dask, Ray, Spark
(PySpark), где та же идея масштабируется на кластер (модель MapReduce).

## Тема 4. Базы данных

### Билет 4.1

> Основные понятия реляционной и объектной моделей данных.

**Ответ.**

**Модель данных** — совокупность структур данных, операций над ними и ограничений целостности.

**Реляционная модель** (Э. Кодд, 1970) основана на теории множеств и логике предикатов.
- *Домен* — множество допустимых значений атрибута; *атрибут* — пара «имя : домен».
- *Отношение* (таблица) — подмножество декартова произведения доменов: заголовок (схема, набор
  атрибутов) + тело (множество кортежей). Кортеж = строка, атрибут = столбец, степень = число
  атрибутов, кардинальность = число кортежей.
- Свойства: порядок строк и столбцов не важен, дубликатов строк нет, все значения атомарны
  (1НФ), особое значение `NULL` — «значение неизвестно» (трёхзначная логика).
- *Ключи:* потенциальный (candidate) — минимальный уникальный набор атрибутов; **первичный
  ключ** — выбранный потенциальный; **внешний ключ** — атрибуты, ссылающиеся на первичный
  ключ другого отношения.
- *Целостность:* сущностная (первичный ключ не NULL и уникален), ссылочная (внешний ключ либо
  NULL, либо ссылается на существующий кортеж), доменная, пользовательские ограничения.
- *Операции:* реляционная алгебра — селекция $\sigma$, проекция $\pi$, декартово произведение,
  объединение, разность, соединение $\bowtie$, переименование; они замкнуты (результат — снова
  отношение), что позволяет строить вложенные запросы. Практическая реализация — SQL.
- Достоинства: строгая математическая основа, независимость данных от приложений, декларативность,
  зрелые СУБД и транзакции ACID.

**Объектная модель** возникла из потребности хранить сложные структуры (САПР, ГИС, мультимедиа)
без «impedance mismatch» — несоответствия между объектами языка программирования и плоскими
таблицами.
- Основные понятия: **объект** (уникальный идентификатор OID, состояние = значения атрибутов,
  поведение = методы), **класс/тип**, **инкапсуляция**, **наследование** (иерархия классов),
  **полиморфизм**, сложные и составные атрибуты, ссылки и коллекции вместо соединений.
- Идентичность объекта задаётся OID, а не значением ключа (два разных объекта могут иметь
  одинаковое состояние).
- Стандарт ODMG (ODL, OQL); примеры СУБД: ObjectStore, Versant, db4o, Caché.
- *Достоинства:* естественное представление сложных объектов, навигационный доступ по ссылкам
  (быстрее соединений), единый язык с приложением.
  *Недостатки:* отсутствие общепринятой строгой теории и стандарта, слабее декларативные
  запросы и оптимизация, меньшая распространённость.
- Компромисс — **объектно-реляционные** СУБД (PostgreSQL, Oracle): пользовательские типы,
  массивы, наследование таблиц, JSON/JSONB; а также **ORM**-библиотеки (SQLAlchemy, Hibernate,
  Django ORM), отображающие классы на таблицы.

### Билет 4.2

> Организация и проектирование физического уровня БД. Ключи. Методы индексирования.

**Ответ.**

**Уровни архитектуры (ANSI/SPARC):** внешний (представления пользователей), концептуальный
(логическая схема), **внутренний/физический** (как данные реально хранятся на носителе).
Физическая независимость данных означает, что изменение хранения не требует переписывать приложения.

**Организация физического уровня.** Данные хранятся в файлах, разбитых на **страницы/блоки**
(обычно 4–16 КБ) — единицы обмена с диском и буферным пулом в ОЗУ. Внутри страницы — слоты
записей и заголовок. Способы размещения: неупорядоченный (heap), упорядоченный (sequential),
хешированный, кластеризованный (строки физически упорядочены по ключу), а также
поколоночное хранение (column store — эффективно для аналитики и сжатия). Главный критерий
оптимизации — **число обращений к диску (I/O)**.

**Ключи.** Суперключ (любой уникальный набор), потенциальный (минимальный суперключ), первичный
(выбранный, обычно физически задаёт кластеризацию), альтернативные, внешний ключ; естественный
против суррогатного (автоинкремент, UUID); составной ключ. Ограничения `PRIMARY KEY`, `UNIQUE`,
`FOREIGN KEY` автоматически поддерживаются индексами.

**Индексирование** — дополнительная структура «значение ключа → адрес записи (RID)», ускоряющая
поиск ценой дополнительной памяти и замедления вставки/обновления (индексы надо поддерживать).
- **B-дерево / B⁺-дерево** — основной тип: сбалансированное сильно ветвящееся дерево, все данные
  в листьях, листья связаны в список. Поиск, вставка, удаление — $O(\log_B n)$, на практике 3–4
  обращения к диску. Поддерживает точечный поиск, **диапазонные запросы**, сортировку, префиксный
  поиск, `ORDER BY`/`MIN`/`MAX`.
- **Хеш-индекс** — $O(1)$ на точечное равенство, но не поддерживает диапазоны и сортировку;
  проблема коллизий и расширяемости (расширяемое/линейное хеширование).
- **Битовые карты (bitmap)** — для атрибутов малой кардинальности (пол, статус); быстрые
  операции AND/OR; применяются в хранилищах данных.
- Специальные: R-дерево и его варианты (пространственные данные), GiST/GIN (полнотекстовый поиск,
  JSON, массивы), инвертированный индекс, LSM-дерево (запись-ориентированные NoSQL: Cassandra,
  RocksDB), ANN-индексы (HNSW, IVF) для векторного поиска в AI-системах.
- Классификации: кластеризованный (порядок строк = порядок индекса, только один на таблицу) и
  некластеризованный; плотный и разреженный; первичный и вторичный; составной (важен порядок
  столбцов); покрывающий (index-only scan); частичный; уникальный.

Выбор индексов — часть физического проектирования: их строят под реальные запросы (анализ плана
выполнения `EXPLAIN`), избегая избыточных индексов на часто изменяемых таблицах.

### Билет 4.3

> Проектирование реляционных баз данных с использованием семантических моделей.

**Ответ.**

Проектирование ведётся сверху вниз: анализ предметной области → **концептуальная (семантическая)
модель**, независимая от СУБД → логическая (реляционная) схема → физическая схема.

**Модель «сущность–связь» (ER-модель, П. Чен, 1976)** — основная семантическая модель.
- **Сущность (entity)** — объект предметной области (Студент, Курс); *набор сущностей* —
  множество однотипных объектов; на диаграмме — прямоугольник.
- **Атрибуты** — свойства сущностей (простые/составные, однозначные/многозначные, производные,
  ключевые).
- **Связь (relationship)** — ассоциация между сущностями (ромб), характеризуется:
  *степенью* (бинарная, тернарная), *кардинальностью* (1:1, 1:N, M:N) и *классом принадлежности*
  (обязательное/необязательное участие, модальность). Нотации: Чена, «воронья лапка» (crow's foot),
  IDEF1X, UML-диаграммы классов.
- **Слабая сущность** — не имеет собственного полного ключа и существует только вместе с
  родительской.
- Расширенная ER-модель (EER) добавляет обобщение/специализацию (наследование), категории,
  агрегацию.

**Правила перехода ER → реляционная схема:**
1. Каждый набор сущностей → отношение; ключевые атрибуты → первичный ключ.
2. Связь 1:1 → внешний ключ в одном из отношений (обычно на стороне обязательного участия) либо
   слияние таблиц.
3. Связь 1:N → внешний ключ в отношении на стороне «N».
4. Связь M:N → **отдельное связующее отношение** с составным первичным ключом из внешних ключей
   обеих сторон (+ собственные атрибуты связи).
5. Многозначные атрибуты → отдельное отношение.
6. Иерархия наследования → одна общая таблица с дискриминатором, таблица на класс или таблица
   на конкретный класс.

**Нормализация** — доведение схемы до нормальных форм для устранения избыточности и аномалий
вставки/удаления/обновления, на основе функциональных зависимостей:
1НФ (атомарность значений) → 2НФ (нет зависимости неключевых атрибутов от части составного
ключа) → 3НФ (нет транзитивных зависимостей) → НФБК (детерминант каждой ФЗ — потенциальный ключ)
→ 4НФ, 5НФ. Требуется сохранение зависимостей и декомпозиция без потерь.
В аналитических хранилищах, наоборот, применяют **денормализацию** (схема «звезда»/«снежинка»:
таблица фактов + таблицы измерений) — ради скорости чтения и меньшего числа соединений.

### Билет 4.4

> Обобщенная архитектура, состав и функции системы управления базой данных (СУБД). Характеристика современных технологий БД. Примеры соответствующих СУБД.

**Ответ.**

**СУБД** — комплекс программных средств для создания, ведения и совместного использования базы
данных множеством пользователей.

**Основные функции:** хранение и организация данных; поддержка языков определения и
манипулирования данными (DDL/DML); обработка и **оптимизация запросов**; управление
**транзакциями** (ACID: атомарность, согласованность, изолированность, долговечность) и
параллельным доступом (блокировки, MVCC, уровни изоляции); журнализация, резервное копирование
и **восстановление** после сбоев; управление буферами ОЗУ; поддержка целостности данных;
безопасность и разграничение доступа; словарь-справочник данных (метаданные).

**Обобщённая архитектура (компоненты):**
- **процессор запросов**: парсер и семантический анализ → преобразование в реляционную алгебру →
  **оптимизатор** (правила и стоимостная модель на основе статистики) → генератор плана →
  исполнитель;
- **менеджер транзакций**: планировщик, менеджер блокировок, журнал (WAL), менеджер восстановления;
- **менеджер данных/хранилища**: менеджер файлов и страниц, буферный пул, менеджер индексов;
- **словарь данных (каталог)**, утилиты администрирования, интерфейсы (CLI, ODBC/JDBC, драйверы).
Архитектурно системы бывают файл-серверные, клиент-серверные, трёхзвенные, встраиваемые (SQLite),
распределённые и облачные (DBaaS).

**Современные технологии БД и примеры СУБД:**
- *Реляционные (OLTP)*: PostgreSQL, MySQL, Oracle Database, MS SQL Server, SQLite.
- *NoSQL* (гибкая схема, горизонтальное масштабирование, теорема CAP, BASE вместо ACID):
  документные — MongoDB, CouchDB; ключ-значение — Redis, DynamoDB; колоночные (wide-column) —
  Cassandra, HBase; графовые — Neo4j, ArangoDB.
- *NewSQL* (масштабируемость NoSQL + ACID и SQL): CockroachDB, TiDB, YDB, Google Spanner.
- *Аналитические / OLAP и колоночные хранилища*: ClickHouse, Vertica, Greenplum, Snowflake,
  BigQuery; форматы Parquet/ORC; концепции Data Warehouse, Data Lake, Lakehouse (Delta Lake, Iceberg).
- *Big Data*: Hadoop HDFS + MapReduce, Apache Spark, Hive, потоковая обработка Kafka + Flink.
- *Специализированные*: временные ряды (InfluxDB, TimescaleDB), полнотекстовый поиск
  (Elasticsearch), векторные БД для AI/RAG (Milvus, Qdrant, pgvector).

### Билет 4.5

> Язык SQL. Средства определения и изменения схемы БД, определения ограничений целостности. Контроль доступа. Средства манипулирования данными.

**Ответ.**

**SQL** (Structured Query Language) — декларативный (непроцедурный) язык работы с реляционными
БД: пользователь описывает *что* нужно получить, а оптимизатор выбирает, *как*. Стандартизован
(SQL-92, SQL:1999, …, SQL:2016+), диалекты СУБД различаются деталями. Делится на подъязыки:
DDL, DML, DCL, TCL.

**DDL — определение и изменение схемы:**
```sql
CREATE DATABASE / SCHEMA ...;
CREATE TABLE orders (
    id          SERIAL PRIMARY KEY,
    customer_id INT NOT NULL REFERENCES customers(id) ON DELETE CASCADE,
    amount      NUMERIC(12,2) CHECK (amount > 0),
    status      VARCHAR(20) DEFAULT 'new',
    created_at  TIMESTAMP NOT NULL,
    UNIQUE (customer_id, created_at)
);
ALTER TABLE orders ADD COLUMN discount NUMERIC(5,2);
ALTER TABLE orders DROP CONSTRAINT ...;
CREATE INDEX idx_orders_created ON orders(created_at);
CREATE VIEW v_big_orders AS SELECT * FROM orders WHERE amount > 100000;
DROP TABLE orders;   TRUNCATE TABLE orders;
```

**Ограничения целостности:** `NOT NULL`, `DEFAULT`, `PRIMARY KEY` (сущностная целостность),
`UNIQUE`, `CHECK` (доменные и пользовательские правила), `FOREIGN KEY ... REFERENCES`
(ссылочная целостность) с правилами реакции `ON DELETE / ON UPDATE`:
`CASCADE`, `SET NULL`, `SET DEFAULT`, `RESTRICT / NO ACTION`. Более сложные правила реализуются
триггерами и хранимыми процедурами; ограничения можно объявлять отложенными (`DEFERRABLE`).

**DCL — контроль доступа** (дискреционная модель): привилегии выдаются пользователям и **ролям**.
```sql
CREATE ROLE analyst;
GRANT SELECT, INSERT ON orders TO analyst;
GRANT analyst TO ivanov;
REVOKE INSERT ON orders FROM analyst;
```
Опция `WITH GRANT OPTION` разрешает передавать привилегию дальше. Дополнительные средства:
представления (VIEW) как способ показать только часть данных, row-level security, шифрование,
аудит.

**DML — манипулирование данными:**
```sql
INSERT INTO orders (customer_id, amount, created_at) VALUES (1, 500.00, NOW());
UPDATE orders SET status = 'paid' WHERE id = 42;
DELETE FROM orders WHERE created_at < '2020-01-01';

SELECT c.name,
       COUNT(*)        AS cnt,
       SUM(o.amount)   AS total
FROM   orders o
JOIN   customers c ON c.id = o.customer_id
WHERE  o.created_at >= '2026-01-01'
GROUP BY c.name
HAVING SUM(o.amount) > 100000
ORDER BY total DESC
LIMIT 10;
```
Логический порядок выполнения: `FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT →
ORDER BY → LIMIT`. Средства: соединения (`INNER`, `LEFT/RIGHT/FULL OUTER`, `CROSS`), подзапросы
(скалярные, `IN`, `EXISTS`, коррелированные), теоретико-множественные операции
(`UNION [ALL]`, `INTERSECT`, `EXCEPT`), агрегатные функции (`COUNT`, `SUM`, `AVG`, `MIN`, `MAX`),
`CASE`, CTE (`WITH ... AS`, в т.ч. рекурсивные), **оконные функции**
(`ROW_NUMBER() OVER (PARTITION BY ... ORDER BY ...)`, `LAG`, `SUM() OVER`) — незаменимы в
аналитике. TCL: `BEGIN / COMMIT / ROLLBACK / SAVEPOINT`, `SET TRANSACTION ISOLATION LEVEL`.

## Тема 5. Методологические вопросы разработки ПО

### Билет 5.1

> Определение методологии разработки ПО, ее свойства и запись. Водопадная модель разработки. Agile Manifesto. Принципы agile. Гибкие методологии разработки ПО.

**Ответ.**

**Методология разработки ПО** — согласованная система принципов, методов, практик, ролей,
артефактов и правил, определяющая, как организован процесс создания программного продукта:
какие есть фазы жизненного цикла, кто что делает, какие документы создаются, как принимаются
решения. Свойства методологии: применимость к определённому классу проектов (масштаб,
критичность, стабильность требований), масштабируемость, повторяемость, измеримость,
поддержка изменений. Формально методология записывается как совокупность: фазы жизненного цикла
(анализ требований → проектирование → реализация → тестирование → внедрение → сопровождение),
роли участников, артефакты, правила перехода между фазами, метрики.

**Водопадная модель (Waterfall, У. Ройс, 1970)** — последовательное, строго упорядоченное
выполнение фаз: каждая начинается после полного завершения предыдущей и утверждения её
документа; возврат назад дорог или не предусмотрен.
*Плюсы:* простота управления и планирования, полная документация, понятные вехи и бюджет,
подходит для проектов с чётко зафиксированными и стабильными требованиями (госзаказ,
встраиваемые и сертифицируемые системы).
*Минусы:* работающий продукт появляется поздно, поздняя обратная связь от заказчика,
дороговизна изменений требований (стоимость исправления ошибки растёт экспоненциально по фазам),
высокие риски.

**Agile Manifesto (2001)** — 4 ценности («слева ценится больше, чем справа»):
1. **Люди и взаимодействие** важнее процессов и инструментов.
2. **Работающий продукт** важнее исчерпывающей документации.
3. **Сотрудничество с заказчиком** важнее согласования условий контракта.
4. **Готовность к изменениям** важнее следования первоначальному плану.

**12 принципов agile** (кратко): наивысший приоритет — удовлетворение заказчика за счёт ранней
и непрерывной поставки ценного ПО; изменение требований приветствуется даже на поздних стадиях;
частая поставка работающего ПО (недели, а не месяцы); ежедневная совместная работа бизнеса и
разработчиков; проекты строятся вокруг мотивированных людей, которым доверяют; личное общение —
самый эффективный способ передачи информации; работающий продукт — основной показатель прогресса;
устойчивый темп разработки неограниченно долго; постоянное внимание к техническому совершенству
и качеству проектирования; простота — искусство минимизации лишней работы; лучшие архитектуры и
решения рождаются у самоорганизующихся команд; регулярная рефлексия и настройка процесса
(ретроспективы).

**Гибкие методологии:** Scrum, Kanban, XP (экстремальное программирование), Lean/Lean Software
Development, Crystal, FDD, DSDM; масштабирование на крупные организации — SAFe, LeSS, Nexus.

### Билет 5.2

> Процесс разработки ПО и организация работы команды. Водопадная модель, V-модель, инкрементальная, спиральная модели.

**Ответ.**

**Процесс разработки** охватывает жизненный цикл ПО: сбор и анализ требований, проектирование
(архитектурное и детальное), кодирование, тестирование (модульное, интеграционное, системное,
приёмочное), внедрение, сопровождение и вывод из эксплуатации. Организация команды включает
роли (менеджер/владелец продукта, аналитик, архитектор, разработчики, тестировщики, DevOps),
структуру (иерархическая, «хирургическая бригада» по Бруксу, самоорганизующаяся кросс-функциональная
команда), коммуникации (митинги, ретроспективы), а также инструменты: система контроля версий,
трекер задач (Jira), CI/CD, код-ревью, стандарты кодирования, документация. Закон Брукса:
«добавление людей в отстающий проект задерживает его ещё больше» — из-за роста числа
коммуникационных связей $n(n-1)/2$ и времени на ввод в курс дела.

**Модели жизненного цикла:**
- **Водопадная** — строго последовательные фазы (см. 5.1); модификация — водопад с обратными
  связями (sashimi).
- **V-модель** — «развёрнутый» водопад: каждой фазе разработки на нисходящей ветви соответствует
  уровень тестирования на восходящей (требования ↔ приёмочное тестирование, архитектура ↔
  системное/интеграционное, детальное проектирование ↔ модульное). Подчёркивает раннее
  планирование тестов и верификацию/валидацию; применяется там, где важна надёжность
  (медицина, авиация, автомобилестроение).
- **Инкрементальная** — система строится и поставляется частями (инкрементами); каждый инкремент
  добавляет функциональность к работающему продукту. Раньше появляется польза, раньше обратная
  связь, но нужна хорошо продуманная архитектура заранее. Родственная — итеративная
  (последовательное уточнение) и итеративно-инкрементальная (RUP).
- **Спиральная (Б. Боэм, 1988)** — итерации-витки, каждый включает 4 сектора: определение целей →
  **анализ и снижение рисков** (в т.ч. прототипирование) → разработка и проверка → планирование
  следующего витка. Главная особенность — управление рисками; подходит для крупных, дорогих,
  инновационных проектов с высокой неопределённостью; недостаток — сложность и требование
  экспертизы в оценке рисков.
- **Гибкие (Scrum/Kanban)** — короткие итерации (спринты 1–4 недели), бэклог, инкремент
  продукта каждую итерацию; см. 5.3.
- **DevOps/непрерывная поставка** — стирание границы между разработкой и эксплуатацией:
  CI/CD, инфраструктура как код, мониторинг, быстрые частые релизы.

Выбор модели определяется стабильностью требований, размером и распределённостью команды,
критичностью системы и требованиями к документации/сертификации.

### Билет 5.3

> Гибкие методологии. Agile-манифест. История и основные положения экстремального программирования. Современные гибкие методологии.

**Ответ.**

**Предпосылки и Agile-манифест** — см. 5.1: в 2001 году 17 практиков зафиксировали 4 ценности и
12 принципов как ответ на тяжеловесные документо-ориентированные процессы.

**Экстремальное программирование (XP), Кент Бек, 1996–1999** — методология для небольших
команд (до ~12 человек) при быстро меняющихся требованиях. Возникло в проекте Chrysler C3;
книга «Extreme Programming Explained» (1999). Идея: взять известные хорошие практики и довести
их «до экстремума» (если ревью полезно — делать его непрерывно, отсюда парное программирование;
если тестирование полезно — писать тесты до кода).

*Ценности XP:* коммуникация, простота, обратная связь, смелость, (позже) уважение.

*Основные практики (12):*
- **планирование игры** (planning game) и пользовательские истории;
- **короткие релизы** (частые небольшие поставки);
- **метафора системы** (общий язык описания архитектуры);
- **простое проектирование** (YAGNI — не делай того, что не требуется сейчас);
- **разработка через тестирование (TDD)**: red → green → refactor, автоматические модульные тесты;
- **рефакторинг** — постоянное улучшение структуры кода без изменения поведения;
- **парное программирование** — двое за одной машиной, непрерывное ревью и обмен знаниями;
- **коллективное владение кодом** — любой может править любой участок;
- **непрерывная интеграция** — сборка и прогон тестов при каждом коммите (несколько раз в день);
- **40-часовая рабочая неделя** — устойчивый темп, отказ от переработок;
- **заказчик на месте** (on-site customer) — представитель бизнеса доступен команде;
- **стандарты кодирования**.

**Современные гибкие методологии:**
- **Scrum** — рамочный процесс: роли (Product Owner, Scrum Master, Developers), артефакты
  (Product Backlog, Sprint Backlog, Increment, Definition of Done), события (спринт, планирование,
  ежедневный скрам, обзор спринта, ретроспектива), эмпирические столпы — прозрачность, инспекция,
  адаптация; метрики: velocity, burndown chart.
- **Kanban** — визуализация потока работ на доске, ограничение WIP (work in progress), управление
  временем цикла (lead/cycle time), непрерывный поток без фиксированных итераций; эволюционные
  изменения существующего процесса.
- **Lean Software Development** — устранение потерь, отложенные решения, поставка «точно вовремя»,
  встраивание качества.
- **Scrumban**, **SAFe / LeSS / Nexus** — масштабирование agile на несколько команд и
  крупные организации.
- Практики XP (TDD, CI/CD, парное программирование, рефакторинг) сегодня используются
  независимо от выбранной методологии и составляют основу DevOps-культуры.

*Критика и границы применимости:* agile плохо подходит для проектов с жёстко фиксированным
контрактом, объёмом и сроками, для систем повышенной критичности и там, где требуется
исчерпывающая сертификационная документация; часто встречается «карго-культ» — соблюдение
ритуалов без принятия ценностей.

## Тема 6. Инструменты разработки ПО

### Билет 6.1

> Командные оболочки, языки сценариев командных оболочек. Командные оболочки различных семейство операционных систем (Windows, Unix-подобных).

**Ответ.**

**Командная оболочка (shell)** — программа-интерпретатор, обеспечивающая интерфейс между
пользователем и ядром ОС: принимает команды (интерактивно или из скрипта), разбирает их,
запускает программы, управляет их вводом-выводом и возвращает результат. Оболочка — это и
интерактивная среда, и полноценный язык программирования (переменные, ветвления, циклы, функции).

**Общие возможности:** запуск программ с аргументами; **перенаправление ввода-вывода**
(`>`, `>>`, `<`, `2>`); **конвейеры (pipes)** `cmd1 | cmd2` — вывод одной программы становится
вводом другой (принцип Unix: «делай одну вещь хорошо» и текстовый обмен); подстановка имён файлов
(globbing `*`, `?`, `[]`); подстановка команд `$(cmd)`; переменные и переменные окружения
(`PATH`, `HOME`); управление заданиями (`&`, `jobs`, `fg`, `bg`), сигналы; история команд,
автодополнение, псевдонимы (`alias`); скрипты с шебангом `#!/bin/bash` и кодом возврата
(`$?`, 0 = успех).

**Unix-подобные системы:**
- `sh` (Bourne shell, POSIX-стандарт), **`bash`** (Bourne Again Shell — де-факто стандарт Linux),
  `zsh` (по умолчанию в macOS, богатая настройка, oh-my-zsh), `ksh`, `csh/tcsh` (C-подобный
  синтаксис), `fish` (дружелюбный, но не POSIX-совместимый), `dash` (быстрый, для системных скриптов).
- Экосистема утилит: `ls`, `cd`, `grep`, `sed`, `awk`, `find`, `xargs`, `cut`, `sort`, `uniq`,
  `wc`, `tar`, `ssh`, `curl`. Пример конвейера:
  `cat access.log | awk '{print $1}' | sort | uniq -c | sort -rn | head -5`.

**Windows:**
- `command.com` (MS-DOS) → **`cmd.exe`** (пакетные файлы `.bat`/`.cmd`, ограниченные возможности);
- **PowerShell** — объектно-ориентированная оболочка на базе .NET: по конвейеру передаются не
  строки, а **объекты**; команды в форме «Глагол-Существительное» (`Get-ChildItem`, `Where-Object`,
  `Select-Object`), поддержка .NET-типов, удалённое управление (WinRM), кроссплатформенность
  (PowerShell Core 6+ работает на Linux/macOS);
- **WSL** (Windows Subsystem for Linux) даёт полноценный Linux-shell внутри Windows.

**Языки сценариев более высокого уровня:** Python, Perl, Ruby, JavaScript (Node.js) —
используются, когда логика сценария сложна (структуры данных, работа с API, обработка ошибок);
shell остаётся оптимальным для склейки утилит и автоматизации системных операций (сборка,
деплой, cron-задачи, CI-скрипты, Dockerfile).

### Билет 6.2

> Системы программирования (СП), типовые компоненты СП: языки, трансляторы, редакторы связей, отладчики, текстовые редакторы. Модульное программирование. Типы модулей. Связывание модулей по управлению и данным.

**Ответ.**

**Система программирования (СП)** — комплекс инструментальных средств, обеспечивающих полный
цикл создания программ на некотором языке: от написания исходного текста до получения
исполняемого модуля и его отладки.

**Типовые компоненты:**
- **Язык программирования** (синтаксис, семантика) и его стандартная библиотека.
- **Транслятор** — переводит исходный текст в машинный код или промежуточное представление.
  Виды: **компилятор** (полный перевод перед выполнением: C, C++, Rust, Go), **интерпретатор**
  (пооператорное выполнение: shell, ранние Basic), смешанная схема с байт-кодом и виртуальной
  машиной (Java, C#, Python), JIT-компиляция во время выполнения (JVM HotSpot, PyPy, V8).
  Фазы компиляции: лексический анализ → синтаксический (разбор, AST) → семантический →
  генерация промежуточного кода → оптимизация → генерация целевого кода.
- **Редактор связей (компоновщик, linker)** — объединяет объектные модули и библиотеки в
  единый исполняемый файл: разрешает внешние ссылки на символы, распределяет адреса, добавляет
  код из статических библиотек (`.a`, `.lib`); для динамических библиотек (`.so`, `.dll`)
  связывание откладывается на этап загрузки (загрузчик, динамический компоновщик).
- **Отладчик (debugger)** — пошаговое выполнение, точки останова (breakpoints), просмотр и
  изменение переменных, стек вызовов, просмотр памяти (gdb, lldb, pdb, встроенные в IDE).
- **Текстовый редактор**, а также ассемблер, профилировщик, средства сборки (make, CMake,
  Maven, Gradle), система контроля версий, средства тестирования. Объединение всего в единой
  оболочке — **IDE** (Visual Studio, IntelliJ IDEA, PyCharm, VS Code).

**Модульное программирование** — принцип декомпозиции программы на относительно независимые
части (модули) с чётко определённым интерфейсом и скрытой реализацией (принцип **сокрытия
информации** Д. Парнаса). Цели: управление сложностью, повторное использование, раздельная
компиляция, параллельная разработка, локализация изменений и упрощение тестирования.
Критерии качества: **сильное зацепление (cohesion)** внутри модуля и **слабое связывание
(coupling)** между модулями.

**Типы модулей:** по назначению — библиотечные (функциональные), модули данных, интерфейсные,
управляющие (главный модуль), утилитные; по способу подключения — статические и динамические
(DLL/SO, загружаемые во время выполнения); по языковой реализации — процедуры и функции,
пакеты/модули (Python-модуль, Java-пакет, Ada package), классы и компоненты, микросервисы
(модульность на уровне архитектуры).

**Связывание модулей.** *По управлению* — передача управления между модулями: вызов процедуры
с возвратом, обработчики событий/колбэки, обмен сообщениями. *По данным* — обмен информацией:
через параметры (по значению, по ссылке — предпочтительный, явный способ), через возвращаемые
значения, через глобальные (общие) области данных — наиболее сильное и нежелательное связывание,
через файлы, БД, сеть. Классификация видов связывания по силе (от лучшего к худшему):
по данным → по образцу (структуре) → по управлению (флаг, влияющий на логику) → по внешним
данным → по общей области → по содержимому (прямое обращение к внутренностям другого модуля).
Разрешение имён при компоновке: внутренние (`static`, приватные) и внешние (`extern`,
экспортируемые) символы.

### Билет 6.3

> Системы управления версиями. Централизованное и распределённое управление версиями. Git Workflow, GitHub Workflow.

**Ответ.**

**Система управления версиями (СКВ, VCS)** — инструмент, сохраняющий историю изменений файлов,
позволяющий вернуться к любой предыдущей версии, узнать, кто и когда внёс изменение, и
организовать параллельную работу нескольких разработчиков.
Ключевые понятия: репозиторий, рабочая копия, коммит (ревизия), ветка (branch), слияние (merge),
конфликт, тег, diff, HEAD.

**Централизованные (CVCS)** — CVS, Subversion (SVN), Perforce, Team Foundation Version Control.
Единый серверный репозиторий хранит всю историю; у разработчиков — только рабочая копия.
*Плюсы:* простая и понятная модель, централизованный контроль доступа и прав по каталогам,
удобство работы с очень большими бинарными файлами.
*Минусы:* единая точка отказа (падение сервера/потеря диска = потеря истории), необходимость
сети для большинства операций (commit, log, diff), «дорогие» ветвления и слияния.

**Распределённые (DVCS)** — Git, Mercurial, Bazaar. Каждый разработчик клонирует **полный
репозиторий вместе со всей историей**, что даёт: работу офлайн, мгновенные локальные операции,
естественное резервирование, дешёвое ветвление, гибкие модели совместной работы
(центральный репозиторий, integration manager, «диктатор и лейтенанты»). Обмен изменениями —
`push`/`pull`/`fetch`. *Минусы:* более высокий порог входа, объём репозитория, слабая
поддержка частичной выгрузки и больших бинарников (решается git-lfs, sparse checkout).

**Git.** Создан Линусом Торвальдсом (2005) для ядра Linux. Хранит не разности, а **снимки
(snapshots)** дерева файлов; объекты (blob, tree, commit, tag) адресуются SHA-1/SHA-256-хешем
содержимого; история — направленный ациклический граф коммитов, что обеспечивает целостность и
неизменность истории.
*Три области:* рабочий каталог → индекс (staging area) → репозиторий.
*Базовые команды:* `git init`, `clone`, `status`, `add`, `commit -m`, `log`, `diff`,
`branch`, `checkout`/`switch`, `merge`, `rebase`, `remote`, `fetch`, `pull`, `push`, `stash`,
`reset`, `revert`, `cherry-pick`, `tag`, `bisect`, `blame`.
Слияние: fast-forward, трёхстороннее (merge commit), rebase (линейная история, но переписывание
истории — нельзя делать для уже опубликованных веток).

**Git Workflow** — соглашения о работе с ветками:
- **Централизованный** — все работают в одной ветке (аналог SVN);
- **Feature Branch** — на каждую задачу отдельная ветка, затем слияние в основную;
- **Git Flow** (В. Дриссен): долгоживущие `master`/`main` (релизы, теги) и `develop`
  (интеграция), плюс временные `feature/*`, `release/*`, `hotfix/*`. Подходит для продуктов с
  версионными релизами; критикуется за сложность при непрерывной поставке;
- **GitHub Flow** — упрощённая модель для CI/CD: единственная всегда готовая к деплою ветка
  `main`; на каждую задачу создаётся короткоживущая ветка → коммиты → **Pull Request** →
  автоматические проверки CI и код-ревью → обсуждение → merge в `main` → немедленный деплой;
- **GitLab Flow** — GitHub Flow плюс ветки окружений (`staging`, `production`);
- **Trunk Based Development** — все коммитят в общий ствол мелкими порциями, незавершённая
  функциональность скрывается за feature-флагами.

**GitHub Workflow / платформенные возможности:** форк и pull request как механизм внешнего
вклада, issues и проектные доски, code review с комментариями к строкам, защищённые ветки и
обязательные проверки, GitHub Actions (CI/CD-пайплайны в YAML), релизы, GitHub Pages, Dependabot.
Хорошие практики: атомарные коммиты, осмысленные сообщения (Conventional Commits),
`.gitignore`, ревью перед слиянием, запрет прямого push в `main`, семантическое версионирование.
