# Теория: короткая версия

Шпаргалка для повторения: минимум формул, только то, без чего ответ не засчитают.
Развёрнутые ответы — в [`theory.md`](theory.md). Порядок билетов тот же.

Как отвечать на экзамене: **определение → формула → 2–3 свойства → пример
применения**. Лучше коротко и верно, чем длинно с ошибкой: содержательная ошибка
обнуляет вопрос целиком.

## Тема 1. Машинное обучение

### Билет 1.1. Задача классификации

Есть объекты с признаками и метки классов. По размеченной выборке строим правило,
которое предсказывает метку для новых объектов. Метка — из конечного набора
(этим отличается от регрессии, где ответ — число).

* Виды: бинарная (2 класса), многоклассовая, многометочная.
* Качество: accuracy, precision, recall, F1, ROC-AUC. При перекосе классов
  accuracy врёт (99% «здоров» — точность 99% при бесполезной модели).
* Типы алгоритмов: метрические (k-NN), логические (деревья, леса, бустинг),
  линейные (логистическая регрессия, SVM), байесовские, нейросети, ансамбли.
* Примеры: спам, скоринг, диагноз по анализам, распознавание цифр, фрод.

### Билет 1.2. Метрические методы, k-NN

Идея: похожие объекты лежат рядом, значит у них одинаковый класс (гипотеза
компактности). Нужна метрика — обычно евклидово расстояние.

**k-NN:** находим k ближайших объектов обучающей выборки и голосуем — какой класс
чаще, тот и ответ.

* Обучения нет вообще, вся работа при предсказании («ленивый» алгоритм).
* k подбирают кросс-валидацией: k=1 — переобучение, слишком большое k —
  всегда самый частый класс.
* Признаки обязательно нормировать, иначе «рубли» задавят «годы».
* Плохо работает в больших размерностях, медленно на больших выборках.

### Билет 1.3. Логистическая регрессия и деревья

**Логистическая регрессия:** считаем линейную комбинацию признаков и прогоняем
через сигмоиду — получаем вероятность класса: $p = \sigma(w^\top x)$,
$\sigma(z) = 1/(1+e^{-z})$. Веса подбираем минимизацией log-loss (градиентным
спуском). Граница между классами — гиперплоскость. Плюсы: вероятности,
интерпретируемые веса, быстро.

**Дерево решений:** цепочка вопросов «признак > порога?», в листьях — ответ.
Строится жадно: на каждом шаге берём вопрос, максимально уменьшающий
неоднородность (энтропия или Джини).

* Плюсы: интерпретируемость, не нужна нормировка, работает со смешанными типами.
* Минусы: переобучение, неустойчивость (чуть меняем данные — другое дерево).
* Лечится ансамблями: случайный лес, градиентный бустинг (CatBoost, XGBoost).

### Билет 1.4. Задача кластеризации

Меток нет (обучение без учителя). Надо самим разбить объекты на группы: внутри
группы похожи, между группами — нет.

* Задача некорректно поставлена: правильного ответа не существует, всё зависит от
  метрики и числа кластеров.
* Качество: силуэт (внутренняя мера), ARI/NMI (если эталон всё-таки есть).
* Типы: иерархические, центроидные (k-means), плотностные (DBSCAN — находит
  кластеры любой формы и шум), вероятностные (GMM, EM), спектральные.
* Примеры: сегментация клиентов, группировка новостей, сжатие цветов картинки,
  поиск аномалий.

### Билет 1.5. Иерархическая кластеризация и k-means

**Иерархическая (агломеративная):** сначала каждый объект — свой кластер, потом
на каждом шаге объединяем два ближайших, пока не останется один. Результат —
дендрограмма, режем её на нужной высоте. Число кластеров заранее не нужно, но
сложность $O(n^3)$ — на больших данных не применить.
Способы мерить расстояние между кластерами: ближний сосед, дальний сосед,
среднее, Уорд (чаще всего).

**k-средних:**
1. выбираем k и начальные центры;
2. каждый объект относим к ближайшему центру;
3. центр пересчитываем как среднее своего кластера;
4. повторяем 2–3 до стабилизации.

Минимизирует сумму квадратов расстояний до центров. Быстрый ($O(nkd)$ за
итерацию), но: k надо задавать (метод локтя), сходится в локальный минимум
(k-means++ и несколько запусков), находит только шарообразные кластеры,
чувствителен к выбросам и масштабу признаков.

## Тема 2. Теория вероятностей и статистика

### Билет 2.1. Основные понятия, независимость

Вероятностное пространство $(\Omega, \mathcal{F}, P)$: множество исходов, набор
событий, мера вероятности. Аксиомы: $P(A) \ge 0$, $P(\Omega) = 1$, для
несовместных событий вероятности складываются.

* $\Omega$ — достоверное событие ($P=1$), $\varnothing$ — невозможное ($P=0$),
  $\bar A$ — противоположное, $P(\bar A) = 1 - P(A)$.
* Несовместные события не могут произойти вместе: $A \cap B = \varnothing$.
* $P(A \cup B) = P(A) + P(B) - P(A \cap B)$.
* Условная вероятность: $P(A\mid B) = P(AB)/P(B)$. Байес:
  $P(H\mid A) = P(A\mid H)P(H)/P(A)$.

**Независимость:** $P(AB) = P(A)P(B)$, то есть знание о $B$ не меняет
вероятность $A$.

* **Попарная** — равенство выполняется для каждой пары.
* **В совокупности** — для любого набора событий сразу.
* В совокупности ⇒ попарно, **наоборот неверно**. Пример Бернштейна: тетраэдр с
  гранями красной, синей, зелёной и трёхцветной; события «есть красный/синий/
  зелёный» попарно независимы, но $P(ABC)=1/4 \ne 1/8$.

### Билет 2.2. Случайная величина и её виды

Случайная величина — функция, сопоставляющая каждому исходу число (измеримая,
чтобы вероятности были определены).

* **Дискретная** — конечное или счётное число значений, задаётся таблицей
  $P(\xi = x_i) = p_i$. Примеры: Бернулли, биномиальное, Пуассона, геометрическое.
* **Непрерывная** — задаётся плотностью $f(x)$, вероятность попасть в точку равна
  нулю. Примеры: равномерное, нормальное, показательное, $\chi^2$, Стьюдента.
* Ещё бывают сингулярные (лестница Кантора) и смешанные.

### Билет 2.3. Функция распределения

$F(x) = P(\xi < x)$ — вероятность, что величина меньше $x$. Есть у любой
случайной величины, полностью её задаёт.

Свойства:
1. $0 \le F(x) \le 1$;
2. не убывает;
3. $F(-\infty) = 0$, $F(+\infty) = 1$;
4. непрерывна слева, скачок в точке равен $P(\xi = x)$;
5. $P(a \le \xi < b) = F(b) - F(a)$;
6. для непрерывной величины $F'(x) = f(x)$.

Практика: эмпирическая функция распределения по выборке, критерий
Колмогорова–Смирнова, квантили, генерация случайных чисел через $F^{-1}$.

### Билет 2.4. Матожидание, дисперсия, моменты

**Начальный момент** $\alpha_k = E\xi^k$, **центральный** $\mu_k = E(\xi - E\xi)^k$.
Первый начальный — матожидание, второй центральный — дисперсия, третий — про
асимметрию, четвёртый — про эксцесс.

**Матожидание** — среднее значение: $E\xi = \sum x_i p_i$ или $\int x f(x)dx$.

* $Ec = c$;
* $E(a\xi + b\eta) = aE\xi + bE\eta$ — всегда, независимость не нужна;
* $E(\xi\eta) = E\xi \cdot E\eta$ — только для независимых.

**Дисперсия** — мера разброса: $D\xi = E(\xi - E\xi)^2 = E\xi^2 - (E\xi)^2$.

* $Dc = 0$, $D(c\xi) = c^2 D\xi$, $D(\xi + c) = D\xi$;
* $D(\xi + \eta) = D\xi + D\eta$ для независимых;
* $\sigma = \sqrt{D\xi}$ — в тех же единицах, что и величина.

По выборке: $\bar X = \frac1n\sum X_i$ и $s^2 = \frac{1}{n-1}\sum (X_i-\bar X)^2$
(делитель $n-1$, иначе оценка смещена).

### Билет 2.5. Корреляция и парная регрессия

**Коэффициент корреляции Пирсона** $r = \frac{\mathrm{cov}(X,Y)}{\sigma_X\sigma_Y}$
измеряет **линейную** связь.

* $-1 \le r \le 1$; $|r| = 1$ — точная линейная зависимость; $r = 0$ — линейной
  связи нет.
* Независимость ⇒ $r = 0$, **обратное неверно**: для $Y = X^2$ корреляция нулевая
  при полной зависимости.
* Корреляция ≠ причинность.

**Парная линейная регрессия** $y = \beta_0 + \beta_1 x + \varepsilon$. Метод
наименьших квадратов минимизирует сумму квадратов отклонений:
$$\hat\beta_1 = \frac{\sum(x_i-\bar x)(y_i-\bar y)}{\sum(x_i-\bar x)^2}, \qquad
\hat\beta_0 = \bar y - \hat\beta_1 \bar x$$
Прямая всегда проходит через $(\bar x, \bar y)$. Качество — $R^2$ (доля
объяснённой дисперсии), в парной регрессии $R^2 = r^2$.

## Тема 3. Python

### Билет 3.1. Синтаксис и REPL

Python — интерпретируемый язык с динамической строгой типизацией, автоматической
сборкой мусора. Блоки выделяются **отступами**.

* Типы: неизменяемые `int`, `float`, `str`, `tuple`; изменяемые `list`, `dict`,
  `set`.
* Конструкции: `if/elif/else`, `for`, `while`, `def`, `class`,
  `try/except/finally`, `with`, `import`, `match/case` (3.10+).
* Идиомы: списковые включения `[f(x) for x in xs]`, распаковка, `enumerate`,
  `zip`, срезы, f-строки, генераторы с `yield`, декораторы.

**REPL** — Read-Eval-Print Loop: интерактивный режим (`python` без аргументов,
приглашение `>>>`). Прочитал команду → вычислил → напечатал результат → ждёт
дальше. Удобен для проверки гипотез, `help()`, `dir()`. Улучшенный вариант —
IPython.

### Билет 3.2. Jupyter, окружения, менеджеры зависимостей

**Jupyter** — ноутбук из ячеек кода и Markdown с сохранённым выводом. Код
выполняет отдельный процесс — ядро (kernel), переменные живут между ячейками.
Плюс — удобный разведочный анализ и графики; минус — скрытое состояние (важен
порядок запуска), плохо ложится в git, тяжело тестировать.

**Виртуальное окружение** — отдельная папка со своим интерпретатором и
библиотеками, чтобы проекты не конфликтовали версиями:
`python -m venv .venv` и активация.

* **pip** — установщик пакетов, `requirements.txt`, `pip freeze`. Просто, но
  конфликты версий не разрешает.
* **pipenv** — `Pipfile` + `Pipfile.lock` (точные версии, воспроизводимость),
  сам создаёт venv.
* **poetry** — `pyproject.toml` + `poetry.lock`, нормальный решатель
  зависимостей, ещё умеет собирать и публиковать пакет.

Типовой проект: `src/` с кодом, `tests/`, `notebooks/`, `data/`,
`pyproject.toml`, `README.md`, `.gitignore`.

### Билет 3.3. Аннотации типов и статический анализ

*В программе написано «статистический», но по смыслу речь о статическом анализе.*

**Аннотации типов** — подсказки о типах: `def f(x: int) -> str:`. Интерпретатор
их **не проверяет**, просто хранит; проверяют внешние инструменты. Нужны для
документации, автодополнения в IDE, раннего обнаружения ошибок.
Средства `typing`: `Optional`, `Union` (`|`), `Any`, `Callable`, `TypeVar`,
`Protocol`, `TypedDict`.

**Статический анализ** — проверка кода без запуска:

* типы — mypy, pyright;
* линтеры (ошибки и стиль) — ruff, flake8, pylint, стандарт PEP 8;
* форматтеры — black, isort;
* безопасность — bandit.

Обычно вешается на pre-commit и CI: не прошёл проверку — не влил код.

### Билет 3.4. Проблемы интерпретатора, память, GIL

Код компилируется в байт-код и исполняется виртуальной машиной — отсюда
медленность и большой расход памяти (всё объект: `int` весит ~28 байт).

**Управление памятью:**
1. **Подсчёт ссылок** — у каждого объекта счётчик, дошёл до нуля — объект удалён.
   Быстро и предсказуемо, но не разбирает циклические ссылки.
2. **Сборщик мусора по поколениям** (`gc`) — добивает циклы. Три поколения:
   молодые объекты проверяются чаще, потому что большинство умирает рано.

**GIL** — глобальная блокировка: в каждый момент байт-код исполняет только один
поток процесса. Нужна для защиты счётчиков ссылок.

* Следствие: потоки **не ускоряют вычисления** (CPU-bound).
* Но помогают на вводе-выводе: при ожидании диска/сети и внутри C-библиотек
  (NumPy) GIL отпускается.
* Обходы: `multiprocessing`, `asyncio`, C-расширения, векторизация, PyPy,
  в 3.13 — экспериментальная сборка без GIL.

### Билет 3.5. Multiprocessing

Запускаем **несколько процессов**, у каждого свой интерпретатор и свой GIL —
получаем настоящий параллелизм на нескольких ядрах.

* `Process` — один процесс вручную; `Pool` с `map` — пул воркеров, самый частый
  вариант; `concurrent.futures.ProcessPoolExecutor` — современный удобный API.
* Обмен данными: `Queue`, `Pipe` (через pickle), `shared_memory` (без
  копирования), синхронизация — `Lock`, `Semaphore`.
* Способы старта: `fork` (быстрый, Linux), `spawn` (Windows/macOS — обязательно
  `if __name__ == "__main__":`, иначе бесконечное порождение процессов).
* Минусы: процесс дорого создавать, аргументы и результаты сериализуются,
  память не общая, отладка сложнее.

**Правило:** считаем — процессы; ждём сеть или диск — потоки/asyncio; данных
очень много — Dask/Spark.

## Тема 4. Базы данных

### Билет 4.1. Реляционная и объектная модели

**Реляционная** (Кодд, 1970) — данные в таблицах (отношениях).

* Строка — кортеж, столбец — атрибут, домен — множество допустимых значений.
* Порядок строк и столбцов не важен, значения атомарны, `NULL` = неизвестно.
* Ключи: потенциальный (минимальный уникальный), первичный (выбранный),
  внешний (ссылка на другую таблицу).
* Целостность: сущностная (первичный ключ уникален и не NULL), ссылочная
  (внешний ключ ссылается на существующую строку).
* Операции — реляционная алгебра: выборка, проекция, соединение, объединение,
  разность. На практике — SQL.

**Объектная** — данные хранятся как объекты языка программирования.

* Объект = идентификатор (OID) + состояние + методы; есть классы, наследование,
  инкапсуляция, полиморфизм, ссылки вместо соединений.
* Плюс: не нужно раскладывать сложные объекты по таблицам (нет impedance
  mismatch). Минус: нет строгой теории и стандарта, слабее оптимизация запросов.
* Компромисс: объектно-реляционные СУБД (PostgreSQL) и ORM (SQLAlchemy,
  Hibernate).

### Билет 4.2. Физический уровень, ключи, индексы

Физический уровень — как данные реально лежат на диске: файлы, разбитые на
**страницы** (4–16 КБ), они же единица чтения в память. Главный критерий
оптимизации — число обращений к диску.

Размещение: куча (без порядка), упорядоченное, хешированное, кластеризованное,
поколоночное (для аналитики).

**Индекс** — структура «значение → адрес строки», ускоряет поиск, но занимает
место и замедляет вставку/обновление.

* **B⁺-дерево** — основной тип: поиск за $O(\log n)$, 3–4 обращения к диску,
  умеет диапазоны, сортировку, `MIN/MAX`.
* **Хеш-индекс** — $O(1)$ на точное равенство, диапазоны не умеет.
* **Bitmap** — для столбцов с малым числом значений (пол, статус).
* Специальные: R-дерево (география), GIN (полнотекст, JSON), LSM (NoSQL),
  HNSW (векторный поиск).
* Кластеризованный индекс задаёт физический порядок строк — он один на таблицу.

### Билет 4.3. Проектирование через семантические модели

Порядок: предметная область → концептуальная (семантическая) модель → логическая
схема → физическая.

**ER-модель** (сущность–связь):

* **сущность** — объект (Студент, Курс), рисуется прямоугольником;
* **атрибуты** — свойства, среди них ключевые;
* **связь** — ассоциация, характеризуется кардинальностью (1:1, 1:N, M:N) и
  обязательностью участия.

**Переход к таблицам:**
1. сущность → таблица, ключ → первичный ключ;
2. связь 1:N → внешний ключ на стороне «N»;
3. связь M:N → отдельная связующая таблица с двумя внешними ключами;
4. многозначный атрибут → отдельная таблица.

**Нормализация** убирает избыточность и аномалии:
1НФ — атомарные значения; 2НФ — нет зависимости от части составного ключа;
3НФ — нет транзитивных зависимостей; НФБК — строже 3НФ.
В хранилищах данных наоборот денормализуют (схема «звезда») ради скорости чтения.

### Билет 4.4. Архитектура и функции СУБД

**СУБД** — программа для создания и совместного использования базы данных.

**Функции:** хранение данных, языки DDL/DML, обработка и оптимизация запросов,
транзакции (ACID) и параллельный доступ, журналирование и восстановление после
сбоя, управление буферами, целостность, безопасность, словарь метаданных.

**Компоненты:**
* процессор запросов: парсер → оптимизатор (по статистике выбирает план) →
  исполнитель;
* менеджер транзакций: блокировки/MVCC, журнал WAL, восстановление;
* менеджер хранилища: файлы, страницы, буферный пул, индексы;
* словарь данных, утилиты, интерфейсы (ODBC/JDBC).

**Современные технологии:**
* реляционные: PostgreSQL, MySQL, Oracle, SQLite;
* NoSQL: MongoDB (документы), Redis (ключ-значение), Cassandra (колоночная),
  Neo4j (графовая) — гибкая схема, горизонтальное масштабирование, CAP;
* NewSQL: CockroachDB, YDB — масштабируемость плюс ACID;
* аналитические: ClickHouse, Snowflake, BigQuery, формат Parquet;
* Big Data: Hadoop, Spark, Kafka;
* специальные: InfluxDB (временные ряды), Elasticsearch (поиск), Qdrant (векторы).

### Билет 4.5. Язык SQL

SQL — декларативный язык: описываем *что* нужно, а *как* решает оптимизатор.

**DDL — схема:** `CREATE TABLE`, `ALTER TABLE`, `DROP`, `CREATE INDEX`,
`CREATE VIEW`.

**Ограничения целостности:** `NOT NULL`, `DEFAULT`, `PRIMARY KEY`, `UNIQUE`,
`CHECK`, `FOREIGN KEY ... REFERENCES` с `ON DELETE CASCADE / SET NULL / RESTRICT`.

**DCL — доступ:** `GRANT SELECT, INSERT ON t TO role;`, `REVOKE ...`,
роли, `WITH GRANT OPTION`.

**DML — данные:** `INSERT`, `UPDATE`, `DELETE`, `SELECT`.

```sql
SELECT c.name, SUM(o.amount) AS total
FROM   orders o JOIN customers c ON c.id = o.customer_id
WHERE  o.created_at >= '2026-01-01'
GROUP  BY c.name
HAVING SUM(o.amount) > 100000
ORDER  BY total DESC
LIMIT  10;
```

Порядок выполнения: `FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT`
(поэтому в `WHERE` нельзя использовать псевдоним из `SELECT`).
Ещё: соединения (`INNER`, `LEFT`), подзапросы, `UNION`, агрегаты, `CASE`,
CTE (`WITH`), оконные функции (`ROW_NUMBER() OVER (PARTITION BY ...)`).
Транзакции: `BEGIN / COMMIT / ROLLBACK`.

## Тема 5. Методологии разработки

### Билет 5.1. Методология, водопад, Agile

**Методология** — набор принципов, практик, ролей и правил: кто что делает, в
каком порядке, какие документы создаются.

**Водопад:** требования → проектирование → кодирование → тестирование →
внедрение → сопровождение. Каждая фаза начинается после полного завершения
предыдущей, возврат назад дорог.
Плюсы: простое планирование, полная документация, понятные сроки. Минусы:
продукт видно только в конце, изменение требований стоит очень дорого.

**Agile Manifesto (2001), 4 ценности:**
1. люди и взаимодействие важнее процессов и инструментов;
2. работающий продукт важнее документации;
3. сотрудничество с заказчиком важнее контракта;
4. готовность к изменениям важнее следования плану.

12 принципов если коротко: частая поставка работающего ПО, изменения
приветствуются на любой стадии, ежедневная работа с бизнесом, мотивированные
самоорганизующиеся команды, живое общение, устойчивый темп, техническое
совершенство, простота, регулярные ретроспективы.

Гибкие методологии: Scrum, Kanban, XP, Lean; масштабирование — SAFe, LeSS.

### Билет 5.2. Процесс разработки и модели жизненного цикла

Жизненный цикл: требования → проектирование → кодирование → тестирование →
внедрение → сопровождение. Команда: владелец продукта, аналитик, архитектор,
разработчики, тестировщики, DevOps. Инструменты: git, трекер задач, CI/CD,
код-ревью.
Закон Брукса: добавление людей в отстающий проект задерживает его ещё больше
(растёт число связей между людьми).

**Модели:**
* **Водопадная** — строго последовательные фазы.
* **V-модель** — тот же водопад, но каждой фазе слева соответствует уровень
  тестирования справа (требования ↔ приёмочные тесты, архитектура ↔
  интеграционные, детальный дизайн ↔ модульные). Для надёжных систем: медицина,
  авиация.
* **Инкрементальная** — продукт наращивается работающими частями.
* **Спиральная** (Боэм) — витки, на каждом обязательный **анализ рисков** и
  прототип. Для больших дорогих проектов с неопределённостью.
* **Гибкие** — короткие итерации-спринты.
* **DevOps** — CI/CD, частые релизы, инфраструктура как код.

### Билет 5.3. Гибкие методологии и XP

Agile-манифест — см. билет 5.1.

**Экстремальное программирование (XP)**, Кент Бек, конец 1990-х, проект в
Chrysler. Идея: взять хорошие практики и довести их до предела (ревью полезно —
делаем непрерывно, то есть парное программирование).
Ценности: коммуникация, простота, обратная связь, смелость, уважение.

**Практики:** планирование по пользовательским историям, короткие релизы, простой
дизайн (YAGNI), **TDD** (сначала тест, потом код), постоянный рефакторинг,
**парное программирование**, коллективное владение кодом, **непрерывная
интеграция**, 40-часовая неделя, заказчик рядом с командой, стандарты кодирования.

**Scrum:** роли — Product Owner, Scrum Master, команда; артефакты — product
backlog, sprint backlog, инкремент; события — спринт (1–4 недели), планирование,
ежедневный митинг, обзор, ретроспектива.

**Kanban:** доска, визуализация потока, ограничение числа задач в работе (WIP),
без фиксированных итераций.

Практики XP (TDD, CI/CD, ревью) сегодня используют независимо от методологии.

## Тема 6. Инструменты разработки

### Билет 6.1. Командные оболочки

**Оболочка (shell)** — программа, которая принимает команды пользователя,
запускает программы и возвращает результат. Одновременно язык программирования:
переменные, ветвления, циклы, функции.

Возможности: перенаправление ввода-вывода (`>`, `<`, `2>`), **конвейеры**
`cmd1 | cmd2`, шаблоны имён файлов (`*`), подстановка команд `$(...)`, переменные
окружения (`PATH`), фоновые задачи (`&`), скрипты с `#!/bin/bash`, код возврата
`$?` (0 — успех).

* **Unix:** `sh` (POSIX-стандарт), **bash** (стандарт Linux), `zsh` (macOS),
  `fish`, `dash`. Утилиты: `grep`, `sed`, `awk`, `find`, `xargs`, `sort`, `uniq`.
* **Windows:** `cmd.exe` (bat-файлы, слабый), **PowerShell** — по конвейеру идут
  не строки, а **объекты** .NET, команды вида «Глагол-Существительное»
  (`Get-ChildItem`); есть WSL для полноценного Linux-шелла.

Когда логика сложная — берут Python/Perl; shell хорош для склейки утилит,
деплоя, CI-скриптов.

### Билет 6.2. Системы программирования и модульность

**Система программирования** — набор инструментов для написания, сборки и отладки
программ.

**Компоненты:**
* **язык** и его стандартная библиотека;
* **транслятор**: компилятор (весь код заранее — C, Go), интерпретатор
  (по строчке), смешанно через байт-код и виртуальную машину (Java, Python),
  JIT. Фазы компиляции: лексический → синтаксический (AST) → семантический
  анализ → генерация кода → оптимизация;
* **редактор связей (компоновщик)** — собирает объектные модули и библиотеки в
  исполняемый файл, разрешает ссылки на внешние символы; для динамических
  библиотек (`.dll`, `.so`) связывание при загрузке;
* **отладчик** — точки останова, пошаговое выполнение, просмотр переменных;
* текстовый редактор, профилировщик, система сборки; всё вместе — IDE.

**Модульное программирование** — разбиение программы на модули с чётким
интерфейсом и скрытой реализацией. Цели: борьба со сложностью, повторное
использование, раздельная компиляция, параллельная работа команды.
Критерий качества: **сильная связность внутри модуля, слабое связывание между**.

**Типы модулей:** библиотечные, модули данных, управляющие, интерфейсные;
статические и динамические; функции, пакеты, классы, микросервисы.

**Связывание:** по управлению — вызовы процедур, события, сообщения; по данным —
через параметры (лучший вариант), возвращаемые значения, глобальные переменные
(худший вариант), файлы, БД.

### Билет 6.3. Системы контроля версий, Git

**СКВ** хранит историю изменений: можно откатиться к любой версии, увидеть, кто и
когда что менял, и работать нескольким людям параллельно.

**Централизованные** (SVN, CVS): вся история на сервере, у разработчика только
рабочая копия. Просто и управляемо, но сервер — единая точка отказа, для коммита
нужна сеть, ветвление дорогое.

**Распределённые** (Git, Mercurial): у каждого полная копия репозитория со всей
историей. Работа офлайн, быстрые операции, дешёвые ветки, естественный бэкап.

**Git** (Торвальдс, 2005): хранит снимки состояния файлов, объекты адресуются
хешем, история — граф коммитов.
Три области: рабочий каталог → индекс (staging) → репозиторий.
Команды: `init`, `clone`, `add`, `commit`, `status`, `log`, `diff`, `branch`,
`checkout`, `merge`, `rebase`, `pull`, `push`, `stash`, `revert`.

**Workflow:**
* **Feature Branch** — ветка на задачу, потом слияние;
* **Git Flow** — постоянные `main` и `develop` плюс временные `feature/*`,
  `release/*`, `hotfix/*`; для продуктов с версиями;
* **GitHub Flow** — одна ветка `main`, всегда готовая к деплою; задача → ветка →
  **Pull Request** → автотесты и код-ревью → merge → деплой;
* **Trunk Based** — все коммитят в ствол мелкими порциями, незаконченное прячут
  за feature-флагами.

**GitHub:** форки и pull request, issues, ревью по строкам, защищённые ветки,
GitHub Actions для CI/CD.
